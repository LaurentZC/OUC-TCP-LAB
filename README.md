# OUC-TCP-LAB

2025 年秋《计算机网络》课程洪峰老师 TCP 大实验代码仓库。

本实验目标是实现一个简化版本的 TCP 协议栈，是从 UDP 本体开始开发，涵盖了 TCP 的可靠传输、拥塞控制的内容。

## RDT 1.0

实现最基本的打包与解包功能，这部分由老师提供代码框架，只需要调制一下接口即可。

## RDT 2.0

RDT 2.0 需要解决数据可能的出错问题，因此我们需要实现一个核验机制（基于 CRC32）。

数据正确时，接收方需要发送确认报文段；数据出错时，接收方需要发送否认报文段；

## RDT 2.1

由于 2.0 中接收方和发送方都是停止等待的，而 ACK / NAK 报文段可能出错，会导致双方出现死锁问题。

因此需要实现重传机制，既然需要重传，就必须保证包至少两种状态（区分正常发送和重传）。

## RDT 2.2

2.2 的改进就是使用上一个包的确认号来表达否认，从而可以省略掉 NAK 报文段。

## RDT 3.0

RDT 3.0 需要解决数据或 ACK 可能丢失的问题，因此就需要实现超时重传机制：
需要 `一个` 计数器来确保数据包在超时后被重传，此处需要多线程编程。

## RDT 4.0

由于停止等待协议效率实在太低，因此需要实现流水线机制（滑动窗口协议）来提升效率。

4.0 实现的是 GBN，在一个窗口内，对窗口左沿的包（下称 base 包）进行计时， 超时发生时应该重传窗口内所有包。

在 GBN 中接收方需要累积确认，需要 `一个` 计时器：

- 当 base 包到达时，需要计时 500ms 等待其他报文段
- 当收到乱序包时，应该丢弃改包并立即发送 ACK，后重置计时器

因为滑动窗口可能出现乱序问题，因此我们就必须对包进行编号。

## RDT 4.1

GBN 的效率仍然不够，因此需要实现 Selective Repeat 协议来提升效率：
SR 对每一个包都设置一个计时器，而且是对每一个包进行单独确认，遵循谁超时就重发谁。

## RDT 4.2

4.2 就是 TCP 协议（无流量控制、拥塞控制），简单说就是使用 `一个` 计时器， 在 SR 的基础上增加了累积确认的机制；
或者说是在 GBN 的基础上增加对失序包的缓存（当然不包括重复包）。

## 拥塞控制

拥塞控制主要分为 Tahoe 和 Reno 两个部分

### TCP-Tahoe

Tahoe 包括慢启动、拥塞避免和快重传三个部分：

- 慢启动：每收到一个 ACK [^1]，拥塞窗口增加 1 MSS；当发生超时，ssthresh 设为 cwnd/2，cwnd 设为 1 MSS
- 拥塞避免：每收到一个 ACK，cwnd 增加 1/cwnd MSS；当发生超时，ssthresh 设为 cwnd/2，cwnd 设为 1 MSS
- 快重传：当收到 3 个重复 ACK 时，认为发生了丢包，ssthresh 设为 cwnd/2，cwnd 设为 1 MSS

[^1]:[RFC 5681](https://www.rfc-editor.org/rfc/rfc5681) 如此规定，但是代码中由于累积确认，实际是按照确认的报文段数来增长

### TCP-Reno

Reno 在 Tahoe 的基础上修改了快重传并增加了快恢复机制：

- 快重传：当收到 3 个重复 ACK 时，认为发生了丢包，ssthresh 设为 cwnd/2，cwnd 设为 ssthresh + 3 MSS
- 快恢复：在快重传后，每收到一个重复 ACK，cwnd 增加 1 MSS；当收到新的 ACK 时，cwnd 设为 ssthresh
